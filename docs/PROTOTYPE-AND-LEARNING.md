# Charlie Architect — Concept exploration and feedback

## Propose meaningful differences
When the design direction is genuinely unclear, build 2–3 **distinct** mini-prototypes of the highest-leverage component. Vary concept, composition, typography, product interaction or motion behavior — not just button colors. Compare actual working variants and promote one before building the full page. Do not waste time prototyping when the brief already selects a direction.

## Record design decisions
Capture what problem was solved, options considered, chosen implementation, rationale, related product evidence, trade-offs and approval status.

## Learn taste without overfitting
User feedback belongs first in project-level design guidance (`DESIGN.md` or equivalent), not in Charlie's universal defaults. Write reusable rules only when the user actually approved a general preference; distinguish literal feedback from inferred reasoning.

Examples of actionable rules:
- "Less generic" becomes product-led visual metaphor, non-repeating composition, useful interaction and no placeholder sections.
- "More motion" becomes a coherent narrative and a real signature interaction, not fade-up everywhere.
- A rejected hero is evidence against that design for that product, not against every hero of the same general layout.

## Review loop
Inspect actual viewport and interactions when possible. Flag excessive motion, tactile mismatches, broken real user tasks and layout edge cases. Decide **keep / refine / remove**, then verify corrections before reporting success.

## Stress the UI
Try realistic long/short text, translations, missing data, small screens, zoom, keyboard focus and interrupted input. Make tests specific to real components instead of generic claims.
